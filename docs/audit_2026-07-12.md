# Audit `queue_management` (Odoo 19) + `queue_mobile` (Flutter) — 2026-07-12

Périmètre : module `addons/queue_management` v19.0.1.0.1 (~2 700 lignes) et app
`queue_mobile` (~1 700 lignes Dart). Lecture exhaustive du code, aucun correctif
appliqué à ce stade.

Constat général : socle sain (isolation multi-société des données métier via
record rules, OTP haché avec TTL/anti-rejeu/lockout, jetons secrets restreints
`base.group_system`, templates publics correctement échappés, 42 tests backend).
Les findings ci-dessous sont classés par sévérité.

---

## 🔴 Critique

### C1. `queue.customer` sans isolation multi-tenant (fuite de données personnelles)
`queue.customer` (nom + email des clients mobiles) n'a **ni `company_id` ni
record rule** (`security/queue_record_rules.xml` couvre les 5 autres modèles).
Conséquences :
- un **agent** de l'établissement A lit les clients de l'établissement B
  (ACL `access_queue_customer_agent` read=1, portée globale) ;
- un **responsable** de A peut **modifier/supprimer** les clients de B
  (ACL manager 1,1,1,1 sans restriction).

C'est le point noir du SaaS. Nuance d'architecture : un client mobile est par
nature **global** (il peut visiter plusieurs établissements), donc un simple
`company_id` serait faux. Recommandation : retirer l'accès agent, restreindre
la fiche client aux données strictement nécessaires côté manager, et idéalement
ne montrer à un établissement que les clients **ayant un ticket chez lui**
(record rule sur domaine via tickets), ou réserver le modèle au groupe système.

### C2. Inondation OTP / création de comptes illimitée (`/api/queue/auth/request_otp`)
Toute adresse email postée **crée immédiatement** un `queue.customer` **et un
`res.partner`** puis envoie un email. Le seul garde-fou (60 s) est **par
client**, pas par appelant. Un attaquant peut :
- créer des millions d'enregistrements (pollution DB + annuaire partenaires) ;
- utiliser le serveur comme canon à spam (bombardement d'un tiers : 1 email/60 s
  par adresse, illimité en nombre d'adresses).

Recommandation : rate-limit par IP (réutiliser le pattern PG éprouvé sur
`coconut_website_mobile`), validation email stricte (`odoo.tools.mail.email_normalize`
— aussi contre l'injection d'en-têtes), et ne créer le `res.partner` qu'à la
**première connexion réussie** (OTP vérifié), pas à la demande de code.

## 🟠 Élevé

### E1. Jeton de session éternel, aucune révocation serveur
`queue.customer.token` n'expire jamais et il n'existe **pas d'endpoint logout** :
la déconnexion de l'app efface seulement le stockage local, le jeton reste
valide à vie côté serveur. Un jeton fuité = accès permanent.
Recommandation : endpoint `/api/queue/auth/logout` (révocation), expiration
glissante (ex. 90 jours), et — amélioration — stocker le jeton **haché** en DB
(comme l'OTP) pour qu'un dump DB ne donne pas de sessions valides.

### E2. Fuite de notifications push entre utilisateurs d'un même appareil
`fcm_register` attache le jeton FCM de l'appareil au client connecté, mais rien
ne le détache : après logout + connexion d'un **autre** compte sur le même
téléphone, les deux `queue.customer` gardent le même `fcm_token` → le nouvel
utilisateur reçoit les notifications de tickets de l'ancien.
Recommandation : à l'enregistrement d'un `fcm_token`, le retirer de tout autre
client qui le porte ; et au logout (E1), effacer `fcm_token`.

### E3. Échec SMTP silencieux : « code envoyé » alors que rien n'est parti
`_send_otp_email` fait `mail.send(raise_exception=False)` : si le SMTP échoue,
l'API répond quand même succès et l'utilisateur attend un code qui n'arrivera
jamais (piège déjà documenté sur `association_management`, cf. mémoire
`odoo19_mail_template_qweb_body`). Recommandation : `raise_exception=True`,
capter l'échec dans le contrôleur et renvoyer une erreur explicite.

### E4. Tickets/RDV illimités : flood des files par un compte jetable
- `ticket_create` accepte **n'importe quel `service_id`** (entiers énumérables,
  pas de `qr_token` exigé) : on peut spammer les files de tous les tenants sans
  jamais avoir mis les pieds sur un site (1 ticket actif par file, mais × toutes
  les files de tous les établissements).
- `_book_appointment` n'a **aucune limite** : un même client peut réserver tous
  les créneaux d'une journée (la garde « 1 ticket actif/file » exclut l'état
  `scheduled`).

Recommandation : exiger le `qr_token` du site à la création de ticket « je suis
sur place », plafonner les RDV actifs par client/file (ex. 2), et plafonner les
tickets actifs totaux par client.

## 🟡 Moyen

### M1. Numérotation : doublons possibles sous concurrence
`_next_number` fait un lire-incrémenter-écrire sans verrou : deux créations
simultanées (borne + mobile) peuvent produire deux « B-042 ». Le commentaire du
code l'assume pour la Phase 0 ; pour un SaaS en production c'est à corriger :
`SELECT ... FOR UPDATE` sur la file avant incrément (ou `ir.sequence`).

### M2. Surréservation : contrôle de capacité non verrouillé
`_book_appointment` vérifie la capacité puis crée le ticket sans verrou → deux
réservations simultanées du dernier créneau passent toutes les deux. Même
correctif que M1 (verrou de ligne sur la file).

### M3. Réservation d'un créneau déjà passé
`slots()` (contrôleur) filtre les créneaux passés **pour l'affichage**, mais
`_book_appointment` accepte n'importe quel créneau du jour, y compris passé.
Ajouter la garde côté modèle.

### M4. App : session révoquée non gérée
Si le serveur répond « Non authentifié. » (jeton révoqué/écrasé par une
connexion sur un autre appareil), l'app affiche l'erreur mais ne déconnecte
jamais : l'utilisateur est coincé. Détecter ce cas dans `QueueApi`/écrans et
forcer `logout()` → retour à l'écran de connexion.

### M5. App : listes jamais rafraîchies au retour de navigation
`HomeScreen` charge les tickets une fois dans `initState` ; au retour d'un
`TicketScreen` (annulation, check-in…) la liste est périmée jusqu'au
pull-to-refresh manuel. Rafraîchir au pop de route (ou passer la liste en
provider invalidé).

### M6. Email non normalisé en écriture backend
`create()` normalise l'email mais pas `write()` : une correction manuelle en
backoffice (« Foo@Bar.com ») casse la connexion (recherches en minuscules) et
peut contourner l'unicité logique. Normaliser aussi dans `write()`.

## 🟢 Mineur / améliorations

- **B1.** `slots`/`site` : `service_id` énumérable expose noms de files et
  plannings de tous les tenants sans QR (fuite d'information faible).
- **B2.** Cron no-show RDV : prévenir le client par push quand son RDV expire.
- **B3.** Heures d'ouverture interprétées en UTC — OK pour Abidjan (UTC+0),
  déjà documenté ; à convertir si déploiement hors UTC.
- **B4.** Pas de CSP sur les pages publiques borne/affichage (défense en
  profondeur ; l'échappement est déjà correct).
- **B5.** App : bug de sélection de jour dans `BookingScreen` (comparaison
  jour+mois sans l'année — faux positifs autour du Nouvel An).
- **B6.** App : pas de compte à rebours « renvoyer le code » (l'utilisateur
  découvre la limite de 60 s via un message d'erreur).
- **B7.** App : `10.0.2.2:8069` en clair par défaut — prévoir le profil release
  HTTPS (Android bloque le cleartext par défaut en release).
- **B8.** App : navigation au tap sur une notification push non câblée
  (`ticket_id` est déjà dans le payload).
- **B9.** App : tests quasi absents (2 tests de modèles) ; ajouter des tests du
  client API (Dio mocké) et des écrans clés.
- **B10.** `TicketScreen` ne sonde pas les RDV `scheduled` : un check-in fait
  au guichet n'apparaît pas tant qu'on ne rouvre pas l'écran.

## Phase A — notes de livraison (2026-07-12)

- **C1** : ACL agent supprimée sur `queue.customer` ; manager ramené à lecture/écriture
  (archivage via `active`, pas de création/suppression — les clients s'auto-inscrivent).
  Record rule `rule_queue_customer_manager` : visible seulement si le partenaire miroir a
  un ticket dans une société de l'utilisateur (nouveau one2many `res.partner.queue_ticket_ids`).
- **C2** : rate-limit par IP backé PG (`queue.rate.limit`, `SELECT FOR UPDATE`,
  pattern repris d'`association_management` mais embarqué — le module reste autonome) :
  30 demandes OTP/h (blocage 10 min) et 60 vérifications/5 min par IP, XFF géré.
  `email_normalize` en entrée API + dans `create`/`write` (refuse aussi l'injection
  d'en-têtes). Le `res.partner` n'est créé qu'au premier `verify_otp` réussi.
  Cron quotidien de purge des comptes jamais vérifiés (>30 j) + des buckets obsolètes.
- **E1** : `token` stocke désormais le **hash SHA-256** ; `token_expiry` (90 j) ;
  endpoint `/api/queue/auth/logout` (révocation jeton + FCM). ⚠️ Effet de bord
  d'upgrade : les sessions existantes (jetons en clair) sont invalidées → reconnexion OTP.
- **E2** : `_register_fcm` détache le jeton FCM de tout autre compte (1 appareil =
  1 client) ; le logout efface le `fcm_token`.
- **E3** : `mail.send(raise_exception=True)` ; en cas d'échec SMTP l'API répond
  « L'email n'a pas pu être envoyé » et l'anti-spam 60 s est réarmé.
- Tests : 54 (0 échec) — dont logout/expiration de session, vol de jeton FCM,
  rate-limit, partner différé, purge cron, isolation tenant des clients
  (`TestCustomerTenantIsolation`), SMTP en échec.
- Côté app (Phase C) : appeler `/auth/logout` à la déconnexion et gérer
  « Non authentifié. » par un retour à l'écran de connexion.

## Phase B — notes de livraison (2026-07-12)

- **M1** : `queue.service._next_number` relit le compteur en SQL sous
  `SELECT FOR UPDATE` (helper `_lock_row`) après `flush_recordset` — deux
  créations simultanées (borne + mobile) ne produisent plus de doublon, et un
  batch dans la même transaction reste séquentiel. Écriture du compteur en
  `sudo` : un agent (lecture seule sur la file) peut créer un ticket au guichet.
- **M2/M3** : `_book_appointment` fait TOUTES ses vérifications sous le même
  verrou (avec `invalidate_recordset(['ticket_ids'])` post-verrou) : créneau
  futur obligatoire, doublon même client/même créneau refusé, quota par client
  et par file (`appointment_max_per_customer`, défaut 2, exposé dans la vue),
  puis capacité. La surréservation concurrente du dernier créneau est fermée.
- **E4** : `/api/queue/ticket/create` exige le `qr_token` du site du service
  (preuve de présence — le `service_id` énumérable ne suffit plus) ; l'endpoint
  `/api/queue/site` renvoie le jeton en écho et l'app le conserve
  (`SiteInfo.qrToken`) pour le repasser à la prise de ticket. Plafond global
  `_MAX_ACTIVE_TICKETS = 5` tickets/RDV actifs par client, tous établissements
  confondus (contrôleur, patchable en test).
- **M6** : déjà couvert en Phase A (`email_normalize` dans `write`).
- Tests : 61 backend (0 échec) — batch même transaction, agent lecture seule,
  créneau passé, doublon de créneau, quota RDV libéré à l'annulation, QR requis,
  plafond global ; `flutter analyze` 0 issue, tests Dart verts.
- ⚠️ Contrat API : `ticket/create` sans `qr_token` échoue désormais — une
  vieille version de l'app ne peut plus prendre de ticket (mise à jour app
  requise, faite dans le même commit).

## Phase C — notes de livraison (2026-07-12)

- **M4** : le serveur ajoute un code machine-lisible `auth_required` aux
  erreurs d'authentification (`_err(message, code=...)`, backend v19.0.1.2.1) ;
  côté app, `QueueApi.onAuthError` déclenche `AuthNotifier.logout(revokeServer:
  false)` en un point unique → le routeur ramène à l'écran de connexion.
